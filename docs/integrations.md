# Sending change events to LastGood (REST API)

LastGood correlates "what changed" with "what broke". Anything that changes production can be reported with one HTTP request: a deploy, a feature flag flip, an infrastructure run, a config change.

This guide covers the ingestion endpoint that exists today. Native integrations (GitHub App) are set up from the console's Integrations page. Everything else goes through this API.

## The endpoint

```
POST https://api.lastgood.space/api/change-events
Authorization: Bearer <YOUR_API_KEY>
Content-Type: application/json
```

### Authentication

Create an API key in the console (Integrations page). The key is sent in the `Authorization` header. The backend accepts `Bearer <key>` and also the bare key, but use `Bearer`.

- Keys belong to one organization. Events land in that organization.
- A key can be restricted to one service. Sending an event for a different `service` returns `403`.
- Revoked keys return `401`.
- Keep the key in your CI or tool's secret store, never in the repo.

### Payload

| Field | Required | Notes |
|---|---|---|
| `summary` | yes | One line a human reads during an incident. Say what changed. |
| `service` | yes | The service the change affects, e.g. `payments`. |
| `environment` | yes | e.g. `prod`, `staging`. |
| `type` | yes | Kind of change, e.g. `deployment`, `feature_flag`, `infra`. Free-form string. |
| `source` | yes | Tool that reported it, e.g. `GitHub Actions`, `LaunchDarkly`. |
| `occurred_at` | yes | When the change happened, ISO 8601 (`2026-10-09T10:25:26.374Z`). Must parse as a date. |
| `meta` | no | Free-form JSON object for details: `author`, `commit`, `run_url`, flag key, etc. Defaults to `{}`. |

The event `id` is generated by LastGood. You cannot set it.

### Responses

| Status | Meaning |
|---|---|
| `201` | Created. Body is `{"success": true, "data": { ...the stored event... }}`. |
| `400` | A required field is missing, or `occurred_at` is not a valid date. |
| `401` | Missing, invalid or revoked API key. |
| `403` | Key is restricted to another service, or the Free plan's limit of 2 distinct services is reached. |

### Tips

- Send the event when the change finishes, with `occurred_at` set to the real change time. Correlation depends on that timestamp.
- Use the same `service` and `environment` strings every time. `payments` and `Payments` are different services.
- Put the person in `meta.author` so "who deployed?" has an answer.
- Fail soft in CI: a notification failure should not fail the deploy (see the GitHub Actions example).

## Quick test

```bash
curl -X POST https://api.lastgood.space/api/change-events \
  -H "Authorization: Bearer $LASTGOOD_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "summary": "Manual test event",
    "service": "payments",
    "environment": "staging",
    "type": "deployment",
    "source": "curl",
    "occurred_at": "'"$(date -u +%Y-%m-%dT%H:%M:%S.000Z)"'",
    "meta": { "author": "you@example.com" }
  }'
```

You should get `201`, and the event shows up in the console's Events list.

## Recipe 1: GitHub Actions (deploy event)

Add the key as a repository secret named `LASTGOOD_API_KEY`, then add a step after your deploy step:

```yaml
- name: Report deploy to LastGood
  if: success()
  continue-on-error: true
  env:
    LASTGOOD_API_KEY: ${{ secrets.LASTGOOD_API_KEY }}
  run: |
    curl -sS --fail-with-body -X POST https://api.lastgood.space/api/change-events \
      -H "Authorization: Bearer $LASTGOOD_API_KEY" \
      -H "Content-Type: application/json" \
      -d "$(jq -n \
        --arg summary "Deployed ${GITHUB_REPOSITORY} @ ${GITHUB_SHA::7}" \
        --arg author "${GITHUB_ACTOR}" \
        --arg commit "${GITHUB_SHA}" \
        --arg run_url "${GITHUB_SERVER_URL}/${GITHUB_REPOSITORY}/actions/runs/${GITHUB_RUN_ID}" \
        --arg now "$(date -u +%Y-%m-%dT%H:%M:%S.000Z)" \
        '{summary:$summary, service:"payments", environment:"prod", type:"deployment",
          source:"GitHub Actions", occurred_at:$now,
          meta:{author:$author, commit:$commit, run_url:$run_url}}')"
```

Change `service` and `environment` to match your setup. `jq` is preinstalled on GitHub-hosted runners.

## Recipe 2: Feature flag webhooks (LaunchDarkly-style)

Flag tools send their own fixed JSON body, and they cannot be told to produce LastGood's schema. Put a small relay between the tool and LastGood: a serverless function, or a Zapier / n8n step. The relay maps three things: summary, who, when.

Node relay (works as an HTTP handler on any serverless platform):

```js
// Receives a flag-change webhook, forwards it to LastGood.
// The incoming field names below (title, date, member.email, name) follow
// LaunchDarkly's audit-log webhook shape. Check a real delivery from your
// tool and adjust the mapping before relying on it.
export async function handler(req, res) {
  const e = req.body;
  const payload = {
    summary: e.title || `Flag changed: ${e.name}`,
    service: "payments",
    environment: "prod",
    type: "feature_flag",
    source: "LaunchDarkly",
    occurred_at: new Date(e.date || Date.now()).toISOString(),
    meta: { author: e.member?.email, flag: e.name, raw_kind: e.kind },
  };
  const r = await fetch("https://api.lastgood.space/api/change-events", {
    method: "POST",
    headers: {
      Authorization: `Bearer ${process.env.LASTGOOD_API_KEY}`,
      "Content-Type": "application/json",
    },
    body: JSON.stringify(payload),
  });
  res.status(r.ok ? 200 : 502).end();
}
```

Notes:
- Add the relay's URL as a webhook in your flag tool, and protect it with a secret the tool can send (a header or a path token).
- The same relay shape works for Flagsmith, Unleash and similar tools. Only the input mapping changes.
- If you flip flags from your own code or scripts, skip the relay and call the endpoint directly with `type: "feature_flag"`.

## Recipe 3: HCP Terraform run notifications

HCP Terraform can POST run notifications to a webhook, but the body is its own format. Use a relay the same way:

```js
// Field names (notifications[], run_status, run_url, workspace_name) follow
// HCP Terraform's generic webhook payload. Confirm against a real delivery.
export async function handler(req, res) {
  const run = req.body;
  const n = run.notifications?.[0] || {};
  if (n.run_status !== "applied") return res.status(204).end(); // only report finished applies
  const payload = {
    summary: `Terraform applied in ${run.workspace_name}`,
    service: "infrastructure",
    environment: "prod",
    type: "infra",
    source: "HCP Terraform",
    occurred_at: n.message_timestamp || new Date().toISOString(),
    meta: {
      author: run.run_created_by,
      run_url: run.run_url,
      run_id: run.run_id,
      workspace: run.workspace_name,
    },
  };
  const r = await fetch("https://api.lastgood.space/api/change-events", {
    method: "POST",
    headers: {
      Authorization: `Bearer ${process.env.LASTGOOD_API_KEY}`,
      "Content-Type": "application/json",
    },
    body: JSON.stringify(payload),
  });
  res.status(r.ok ? 200 : 502).end();
}
```

If you run Terraform from CI instead, skip HCP notifications and add the GitHub Actions step from Recipe 1 after `terraform apply`, with `type: "infra"`.

## Recipe 4: Anything else

Any script, cron job, or tool that can run `curl` can report a change:

```bash
curl -X POST https://api.lastgood.space/api/change-events \
  -H "Authorization: Bearer $LASTGOOD_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "summary": "Raised API rate limit from 100 to 500 rps",
    "service": "api-gateway",
    "environment": "prod",
    "type": "config",
    "source": "ops-script",
    "occurred_at": "2026-10-09T10:25:26.374Z",
    "meta": { "author": "jane@example.com", "ticket": "OPS-142" }
  }'
```

Or from JavaScript:

```js
await fetch("https://api.lastgood.space/api/change-events", {
  method: "POST",
  headers: {
    Authorization: `Bearer ${process.env.LASTGOOD_API_KEY}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    summary: "Enabled new checkout flow for 25% of users",
    service: "web",
    environment: "prod",
    type: "feature_flag",
    source: "in-house flags",
    occurred_at: new Date().toISOString(),
    meta: { author: "jane@example.com", flag: "new-checkout", rollout: "25%" },
  }),
});
```

## Troubleshooting

- `401`: wrong key, revoked key, or the `Authorization` header is missing.
- `403` mentioning a restricted service: the key is locked to one service. Use a different key or change `service`.
- `403` mentioning the 2-project limit: the Free plan covers 2 distinct `service` values.
- `400`: check all six required fields and that `occurred_at` is ISO 8601.
- Nothing in the console: check `environment` and `service` filters on the Events page.
